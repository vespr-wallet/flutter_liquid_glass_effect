# Translate string resources to other languages

## Usage Modes

This command can be invoked in three ways:

### 1. Translate all missing strings (no arguments)
Run `flutter pub get` first, then read `l10n_untranslated.json` (at project root) to identify which strings are missing translations. Translate all listed keys.

### 2. Translate specific strings
When the user provides specific string keys, translate only those keys to all languages.

### 3. Translate modified strings (git diff)
When asked to look at git diff or similar, identify English strings that have been **modified** (not newly added). These existing keys need their translations updated across all languages to reflect the English changes.

---

## Instructions

1. **Read the source string** from `lib/l10n/intl_en.arb` to ensure you have the current version.

2. **Translate to all language files** - Find all `intl_*.arb` files in `lib/l10n/` (excluding `intl_en.arb`) and add translations. **Only add the string key, NOT the metadata.** For example, if English has `"buy"` and `"@buy"`, only add the `"buy"` key to other ARB files.

3. **Preserve placeholders exactly** - Variables like `{amount}`, `{name}` must appear in all translations:
   ```json
   "walletBalance": "Balance: {amount} ADA"
   ```

4. **Handle plurals/conditionals correctly** using ICU syntax:
   ```json
   "itemCount": "{count, plural, =0{No items} =1{1 item} other{{count} items}}"
   ```

5. **Preserve markdown formatting** - Keep `**bold**`, `*italic*`, `[links](url)` intact.

## Important Constraints

- **Only modify `.arb` files** - This task should NEVER directly modify any other file types (e.g., `.dart`, `.json` files). The localization dart files and `l10n_untranslated.json` are auto-regenerated by the build process.
- **Metadata stays in English only** - Keys prefixed with `@` (like `@buy`, `@walletBalance`) contain metadata and must only exist in `intl_en.arb`.
- **Maintain consistent style** - Each language has its own formality level/language tone/etc. The new translations must stay consistent with the existing tone.
- **Avoid much longer translations where possible** - If there's a good option for a translation that prevents string length from being larger than the English version, that's the best choice to ensure UI consistency. However, **do not force a bad translation** just to keep the length constraint. This matters more for short strings (under ~20 characters).

## Quality Guidelines
- Keep technical terms (ADA, NFT, wallet) untranslated unless there's an established localized term
